BUILD PHASE 2 — DIGS JOBTRACK
================================

IMPORTANT:
This is PHASE 2 ONLY.

Do NOT rebuild Phase 1.
Do NOT remove, break, or redesign existing Phase 1 functionality.

Phase 1 must remain fully functional:
- Job management
- CSV/XLSX import
- WRKMAN text import
- Customer records
- Call/SMS/WhatsApp
- Contact history
- Statuses
- Priority
- Scheduling
- Postponement
- Expenses
- Reports
- Export

Phase 2 adds LOCATION, GPS, DIRECTIONS, ROUTING and FIELD MOVEMENT.

================================
1. CURRENT LOCATION
================================

Add a reliable:

📍 MY LOCATION

feature.

When the user opens JobTrack and grants permission, obtain the phone's current GPS location.

Display:

Current latitude
Current longitude
Accuracy
Current approximate location/address when available

Show a clear GPS permission state:

LOCATION ENABLED
LOCATION DISABLED
LOCATION PERMISSION REQUIRED
LOCATION UNAVAILABLE

Do not pretend the location is accurate if GPS accuracy is poor.

Provide:

REFRESH LOCATION

button.

Use browser/device geolocation APIs in the web/PWA version.

Keep the architecture ready for deeper native Android GPS integration when packaged as an APK.

================================
2. INDIVIDUAL JOB DIRECTIONS
================================

Every job must have:

📍 DIRECTIONS

When clicked:

Origin:
CURRENT LOCATION

Destination:
CUSTOMER ADDRESS

The system should open the best available map/navigation service with the destination.

Prefer Google Maps on Android when available.

Do not force the user to copy and paste addresses.

The customer address should be passed automatically.

If GPS is unavailable, allow:

USE MANUAL START LOCATION

================================
3. ROUTE TO JOB
================================

Create a dedicated:

START ROUTE

button.

When pressed:

1. Read current GPS location.
2. Confirm destination.
3. Display route information.
4. Allow navigation to begin.
5. Keep the JobTrack job visible while navigating.

The user should be able to return to JobTrack without losing the active route.

Show:

START
DESTINATION
DISTANCE
ESTIMATED TRAVEL TIME

When supported by the mapping provider.

================================

5. ROUTE ORDERING
================================

Implement route sequencing.

Input:

Selected jobs

Allow the user to manually reorder stops.

Display:

OPTIMIZED
MANUAL

route modes.

================================
8. CUSTOMER LOCATION DESCRIPTION
================================

Add:

LOCATION NOTES

Example:

"After Gitar Flyover, opposite XYZ Filling Station, take the junction on the right."

This must be separate from the official customer address.

Reason:

Customer addresses in Nigeria can be incomplete.

The app must preserve both:

OFFICIAL ADDRESS

and

FIELD NAVIGATION DESCRIPTION.

================================
9. MAP VIEW
================================

Add a map screen.

Display:

Current location
Selected customer
Route
Stops

Use a mapping provider that supports:

Road maps
Satellite imagery where available
Markers
Directions
Zoom
Current location

The architecture should make the map provider configurable.

Google Maps should be supported where technically and legally appropriate.

Do not embed Google Maps using an unofficial method.

Use official APIs/SDKs or supported navigation links.

================================
10. SATELLITE VIEW
================================

Provide:

MAP
SATELLITE

Satellite view is primarily for visual confirmation of the surrounding environment.

It should help identify:

Buildings
Roads
Compounds
Landmarks
Large structures
Junctions

Do not claim that satellite imagery is live.

Clearly understand that satellite imagery is normally historical imagery, not a live camera feed.

================================

Do not fabricate photographs of landmarks.

START INSTALLATION

29. LOCATION CONFIDENCE
================================

Customer addresses can be imperfect.

Therefore, every location should have:

LOCATION VERIFIED
LOCATION NOT VERIFIED
CUSTOMER CONFIRMED LOCATION

Do not automatically mark an address verified just because geocoding returned coordinates.

Allow the technician to verify it.

================================
30. GEOCODING
================================

Where possible, convert customer addresses into coordinates.

Store:

Latitude
Longitude

If geocoding fails:

show:

LOCATION COULD NOT BE VERIFIED

and allow manual location selection from the map.

Do not invent coordinates.

================================
31. MAP PROVIDER CONFIGURATION
================================

Create a clean map service abstraction.

Do not hard-code the entire application to one provider.

Prepare for:

Google Maps
OpenStreetMap
Other supported providers

The user should be able to configure API keys where required.

Never expose secret API keys in frontend source code.

================================
32. OFFLINE FIELD SUPPORT
================================

The user may lose internet while travelling.

The application should retain:

Current jobs
Customer information
Route order
Landmark notes
Contact history
Job status

locally.

When internet returns, synchronize data where a backend is available.

The map/navigation service may require internet.

Do not claim full offline Google Maps functionality unless officially supported.

================================
33. GPS ERROR HANDLING
================================

If GPS accuracy is poor:

show:

GPS ACCURACY: 85m

and warning:

"Location accuracy is currently low."

Do not automatically trigger arrival from unreliable GPS.

================================

Buttons:

ENABLE LOCATION
USE MANUAL LOCATION

Never repeatedly request permission without user action.

================================

The application must never encourage unsafe phone use while driving.

show a clear warning:

"Use navigation safely. Do not operate the phone while driving."

The application should prioritize large simple actions.
